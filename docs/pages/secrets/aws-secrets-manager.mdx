# Use AWS Secrets Manager

Use AWS Secrets Manager to keep tool and harness credentials in your AWS
account. Sandboxes receive placeholders. [iron-proxy](https://docs.iron.sh)
reads the real value from Secrets Manager and injects it only for allowed
upstream hosts. Secrets Manager encrypts each value with an AWS KMS key. That
key can be a customer managed key.

## Name the secrets

Each credential is one secret. The name of the secret is the prefix followed by
the placeholder of the credential. The default prefix is `centaur/`. The Codex
credential `OPENAI_API_KEY` is therefore the secret `centaur/OPENAI_API_KEY`.

Store each value as plaintext:

```bash
printf '%s' "$OPENAI_API_KEY" | aws secretsmanager create-secret \
  --region us-east-1 \
  --name centaur/OPENAI_API_KEY \
  --secret-string file:///dev/stdin
```

Add `--kms-key-id` to encrypt the secret with a customer managed key. A tool
secret that declares a `json_key` reads that field from a secret of JSON
key/value pairs.

Every credential that iron-proxy injects needs a secret. These are the harness
credentials:

| Credential | Used for |
|------------|----------|
| `OPENAI_API_KEY` | Codex default |
| `OPENROUTER_API_KEY` | OpenRouter via Codex |
| `META_AI_API_KEY` | Meta AI direct via Codex |
| `AMP_API_KEY` | Amp |
| `ANTHROPIC_API_KEY` | Claude Code |

## Give iron-proxy an AWS identity

iron-proxy reads the secrets through the standard AWS credential chain. The
iron-proxy pods get their identity from their ServiceAccount. Give the role of
that identity this policy. Replace the account, the region, and the key ID:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:us-east-1:123456789012:secret:centaur/*"
    },
    {
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "arn:aws:kms:us-east-1:123456789012:key/1234abcd-12ab-34cd-56ef-1234567890ab"
    }
  ]
}
```

The `kms:Decrypt` statement is necessary only for a customer managed key.

### IRSA

Let the chart create the ServiceAccount with the role annotation:

```yaml
ironProxy:
  secretSource: aws-secrets-manager
  awsSecretsManager:
    region: us-east-1
  serviceAccount:
    create: true
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/centaur-iron-proxy
```

The trust policy of the role must allow the ServiceAccount
`system:serviceaccount:<namespace>:<release>-centaur-iron-proxy`.

### EKS Pod Identity

Let the chart create the ServiceAccount without annotations. Then associate it
with the role:

```bash
aws eks create-pod-identity-association \
  --cluster-name <cluster> \
  --namespace <namespace> \
  --service-account <release>-centaur-iron-proxy \
  --role-arn arn:aws:iam::123456789012:role/centaur-iron-proxy
```

The network policies of the iron-proxy pods allow port 80 of the Pod Identity
agent on `169.254.170.23` and `fd00:ec2::23`.

### An existing ServiceAccount

Set `ironProxy.serviceAccount.name` and keep `create: false` to use a
ServiceAccount that you manage.

### Outside EKS

Add the `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` of an IAM user with
the policy to the infra Secret. Every iron-proxy pod loads that Secret. The
other components that load it also see the keys. A workload identity is
safer. Static keys do not expire.

## VPC endpoints

A VPC endpoint of Secrets Manager or STS with private DNS gives that API a
private address. The network policies of the iron-proxy pods allow only public
upstream addresses. List the address ranges of the endpoints:

```yaml
ironProxy:
  awsSecretsManager:
    vpcEndpointCidrs:
      - 10.0.8.0/24
```

The iron-proxy pods can then reach these ranges on port 443. A range can be
the subnet of the network interfaces of the endpoints or the address of one
interface. Only IRSA calls STS. `ironProxy.upstreamDenyCidrs` does not apply
to these calls. It applies only to the requests of the sandboxes.

## Settings

| Value | Default | Description |
| --- | --- | --- |
| `ironProxy.secretSource` | `onepassword` | Set it to `aws-secrets-manager`. |
| `ironProxy.awsSecretsManager.region` | empty | The AWS region of the secrets. The chart does not render without it. |
| `ironProxy.awsSecretsManager.secretPrefix` | `centaur/` | The text before the placeholder in each secret name. |
| `ironProxy.awsSecretsManager.vpcEndpointCidrs` | empty | The address ranges of private VPC endpoints of Secrets Manager and STS. |
| `ironProxy.secretTtl` | `10m` | How long iron-proxy keeps a value before it reads the secret again. |
| `ironProxy.serviceAccount.create`, `.name`, `.annotations` | `false`, empty, empty | The ServiceAccount of the per-sandbox and Code Mode iron-proxy pods. |

A change of the ServiceAccount does not change the running iron-proxy pods. The
next reuse of a retained sandbox recreates its iron-proxy pod with the new
ServiceAccount.

`centaur-perms` registers tool secrets with the same names. Give it the
deployed settings:

```bash
cargo run -p centaur-perms -- \
  --source-policy aws-secrets-manager \
  --aws-region us-east-1 \
  --tools-dir tools \
  principals grant slack-user-t123-u123 \
  --tool github
```

## Verify

Check the settings of api-rs:

```bash
kubectl exec -n centaur deploy/centaur-centaur-api-rs -- env | \
  grep -E 'FIREWALL_MANAGER_(SECRET_SOURCE|AWS_)|KUBERNETES_IRON_PROXY_SERVICE_ACCOUNT'
```

Check the ServiceAccount of the iron-proxy pods:

```bash
kubectl get pods -n centaur -l centaur.ai/iron-proxy=true \
  -o custom-columns=NAME:.metadata.name,SERVICE_ACCOUNT:.spec.serviceAccountName
```

Then run a tool or harness call that reaches an allowed host. iron-proxy
leaves the placeholder in the request when it cannot read a secret. The
upstream then rejects the request. The iron-proxy log names the secret and the
AWS error in a `failed to fetch secret` line. Check the secret name, the region,
the IAM policy, and the trust policy of the role.
